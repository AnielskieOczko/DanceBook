Semantic results in standard search

Issue #219, epic #203. Notes and Figures search today matches keywords only. The backend from #233 adds items found by meaning and flags each result as keyword, semantic or both. Three ways to show that, each drawn for Notes and Figures at desktop and 375px, with the empty state and the fallback when embeddings are unavailable. Query used throughout: “head dropping”, which a good Note may word as “keep the left side long”.

Every list keeps the columns it has today (Notes: Title, Style, Category, Rating, Figures, Media, Created; Figures: Name, Style, Class, Steps, Source), so a related result is as informative as a keyword hit. Wording says “Note”, never “Material”.

Nothing else is shown: no banner, no empty group. The user gets today’s keyword search. Nothing the user asked for is missing, so no alarm is raised.

  • Backend contract: origin flag per result, as #233 already returns. The related group size is the backend’s “how many semantic results to add”, shown as the count.
  • Sort and filters: the style and rating filters narrow both groups (a related item must still pass the filters). Sorting applies inside each group.
  • htmx: one extra target for the related group, swapped with the table. Frozen fragment ids stay.

Cost: a long keyword list pushes the related group below the fold, so it is only found by scrolling. Mitigation: the count appears next to the result count at the top (“2 results · 3 related”).

Fallback (embeddings unavailable): the list is keyword only, so every chip would read “Keyword”. The Match column and the count split are left out. Same screen as today.

  • Backend contract: origin flag per result in ranking order. An exact figure-name match must outrank a vague similar Note (RAG spec, hybrid ranking).
  • Sort: choosing a column sort reorders by that column, drops relevance order, and keeps the chip. The default sort is Relevance whenever there is a query.

Cost: keyword hits and meaning hits interleave, so a user who types an exact title may see a related row above a loosely matching keyword row. The chip explains it but does not prevent it.

  • Backend contract: origin flag per result, plus the two totals for the toggle. Smart is one request with semantic enabled; Keyword is the request without it, so keyword mode makes no embedding call.
  • Remembering the choice: persisting the last mode per user would need a setting, which this mock does not assume. It could default to Keyword on every visit.
  • Fallback: the only direction where the fallback is visible, because Smart is something the user explicitly asked for.

Cost: most users never touch a toggle, so semantic results go unseen unless the counts draw the eye. It also adds a control to the filter bar of two lists.

Open points for review

  • Match reason text. The backend only says keyword, semantic or both. A snippet such as “mentions: left side long” would need the matching passage returned too, a change to #233 and the knowledge index. None of these mocks needs it.
  • Polish. “Also related” and “Found by meaning” need Polish strings with the same key parity as the rest of the app. “Smart” is the hardest word to translate; a neutral “Wg znaczenia” reads better than a literal one.
  • Scope. The same pattern applies to Notes and Figures only. Choreographies and Collections are untouched, as #203 names only those two.
  • Dashboard assistant box. Not affected; it already uses meaning.
